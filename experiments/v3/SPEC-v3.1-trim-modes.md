# CLM/3.1 — sketch (trim modes)

Status: validated in `RESULTS.md` (this directory). Adds **aggressive trim** to the v3.0 sibling-archive architecture, pushing savings from -21% to -55% live-context tokens at 50 sessions vs raw append.

This file is a focused addendum to `SPEC-v3.0-sketch.md` — the dream-pass architecture is unchanged; only the trim policy is new.

## Why trim

The 50-session bench in `RESULTS.md` showed v3.0's live doc grows ×3.08 vs raw's ×3.51. Savings ratio: -21.4%. Architecture works, but more gently than the "constant-size live doc" pitch implied.

The bottleneck: `[ROLL.CALL]`, `[DREAM.LOG]`, and `[STATE].decisions.live` all grow approximately linearly with thread depth. Only the *delta-vs-session-block* portion shrinks. To make growth sublinear, the live doc must offload old entries from these sections too.

That's what trim mode does.

## Trim defaults (composable, all on by default in v3.1)

| section | live keeps | overflow goes to (sibling archive) |
|---|---:|---|
| `[ROLL.CALL]` | last 10 entries | `[ROLL.CALL.ARCHIVE]` |
| `[DREAM.LOG]` | last 3 entries | `[DREAM.LOG.ARCHIVE]` |
| `[STATE].decisions.live` | last 8 decisions | `[DECISIONS.ARCHIVE]` |

Each of these is independently configurable. The defaults above produce the -55% measured at 50 sessions in `RESULTS.md`. Tuning them is straightforward: more aggressive means smaller live doc but more frequent archive lookups for lineage queries.

The header declares the trim mode so a reading AI knows what's offloaded:

```
;;; trim.mode: aggressive
;;; trim.config: roll_call=10, dream_log=3, decisions_live=8
```

## Format additions in the sibling archive

Three new section types appear in the archive file (only when trim is on):

```
[ROLL.CALL.ARCHIVE]
  ;; older roll-call entries offloaded from live doc
  CLd.Snt4.6 · 2026-04-21 · "session 1: started auth middleware extraction"
  ...
;;

[DREAM.LOG.ARCHIVE]
  ;; older dream-log entries offloaded from live doc
  2026-04-25 evening | CLd.Ops4.7 | dream pass 1 | ...
  ...
;;

[DECISIONS.ARCHIVE]
  ;; older live-decisions offloaded from [STATE].decisions.live
  d1: relocate auth -> internal/auth/middleware.go [session 1]
  ...
;;
```

A reading AI doing a lineage query (e.g. "who first proposed X?") loads the sibling archive and searches across both `[DELTA.session-*]` blocks and these new archive sections.

## What stays the same from v3.0

- Dream-pass protocol: read deltas, apply, write `[STATE]`, archive merged deltas, sign.
- Operation vocabulary: `add` / `update` / `remove` / `revert <id>` / `fix <id>` / `note:`.
- Conflict resolution: chronological for `[STATE]` value; both sides preserved in archive.
- Sibling-archive default (still required; inline-archive remains a ship-against pattern at this thread depth).
- Self-bootstrapping: trim mode is self-documenting from the header line and the archive section names.
- Cross-model compatibility: all family prefixes work identically.

## Empirical results from the bench

Measured by `tokens.py` against the synthetic 50-session thread generated by `gen_50_session.py`:

| variant | live tokens | vs raw |
|---|---:|---:|
| Raw append (CLM/2.1) | 5,726 | (baseline) |
| CLM/3.0 sibling (no trim) | 4,498 | -21.4% |
| **CLM/3.1 trim** | **2,603** | **-54.5%** |
| Prose summary (lossy) | 438 | -92.3% |

Total cost (live + archive, archive loaded only on lineage queries):

| variant | total tokens |
|---|---:|
| CLM/3.0 sibling | 7,033 |
| CLM/3.1 trim | 7,596 |

Trim mode adds ~8% to total storage (because offload sections duplicate session-level info that was already implicit in the deltas). Live-context savings are ~6.5× larger than the storage overhead — favorable trade for any thread that's read more often than it's archived to disk.

## Trade-offs trim mode makes deliberately

1. **Audit-thread visibility.** Old `[ROLL.CALL]` lines aren't in the live doc anymore. A casual reader sees only the last 10 signers; the full history requires loading the sibling. v3.1 declares this explicitly (`trim.mode: aggressive` in header) so a reading AI knows to fetch the sibling for lineage questions.

2. **First-time-reader experience.** A fresh AI opening a v3.1-trim doc gets a compact `[STATE]` and recent activity. To understand the full evolution it must explicitly fetch the archive. Self-bootstrap still works (the format teaches itself), but lineage requires an extra read.

3. **Token cost amortization.** Trim mode optimizes for the common case (live read for current state) and pays a one-time cost when a lineage query comes in. Most reads don't ask "who first decided X?" — they ask "what's the current state and what changed recently?". The trim defaults assume the 80/20 split.

## When NOT to use trim mode

- Threads under ~20 sessions — savings are marginal; complexity not worth it.
- Audit/compliance contexts where every read must show full lineage inline.
- Documents intended for human reading (the offloaded `[ROLL.CALL]` removes the on-page audit trail human readers find meaningful).

For these, use v3.0 with no trim, or even raw v2.1 append.

## Open work

- **Trim threshold tuning.** The defaults (10/3/8) were chosen by intuition; a sweep across configurations on a 100+ session thread would identify the actual elbow.
- **Trim-aware clm-rs.** The parser doesn't validate the new archive section types yet. Easy to add; included in next clm-rs release.
- **Recursive dream pass.** Multiple thread-of-dreams: a meta-archive of old dream-passes that itself gets dreamed. Useful for very long threads (200+); deferred until a 200-session bench shows we need it.
